**Date:** 2026-10-09
**Purpose:** Web-project implementation-readiness review informed by the Miva Buddy Desktop handoff. This is research, not a source approval, legal opinion, or authorization to retrieve or republish third-party content.

### Recommendation

Keep **Remote OK as the only active real-data pilot**, strictly within its existing development metadata/tag/link grant. Do not add another live integration yet.

For a future excerpt-backed pilot, **Himalayas is the preferred candidate for a source-specific permission/terms resolution and bounded technical spike**: targeted search, source publication/expiry fields, a documented API use case for applications, and attribution requirements align best with contextual Learn. This is a conditional engineering preference, **not permission to display excerpts or cache data**. Its terms contain a material ambiguity that must be resolved before those activities. If that cannot be resolved, **Arbeitnow is the fallback candidate for the same permission-first evaluation**, but its feed requires local filtering and its timestamps/links are less suitable for direct, clearly dated evidence. Neither is approved for excerpt-backed production use today. No third-party request or outreach is needed for this audit.

## Recommended evidence workflow

1. **Ground first.** Retrieve only the selected user's course/material passages and retain their page/chunk provenance. Course concept extraction already exists; use a separate, bounded, schema-validated skill/concept mapping that can point back to those passages. Ignore the prompt and model response as proof that a skill is in the lecture.
2. **Select narrowly.** Choose at most a few high-confidence canonical concepts explicitly supported by retrieved lecture text. Keep aliases controlled and distinguish lecture wording from broader inferred concepts. The current canonical-skill helper is a useful start; ranking/selecting a small subset is a future refinement, not a reason to delay lecture answers.
3. **Check approval before retrieval.** Use a source only when its activity-specific approval allows the exact retrieval fields and purpose. If not approved, do not call it. Do not send the uploaded lecture, student identity, or transcript to a jobs source—send only the minimum normalized search terms and, if useful, an explicitly supported region.
4. **Verify from permitted source content.** For excerpt-backed evidence, inspect actual source-provided job text only when retrieval and excerpt use are approved. Apply deterministic whole-term/approved-alias matching to the source text; retain the exact supporting sentence and its source provenance. Source tags or categories can produce only a labeled tag/category match, never a claim about description wording. AI may explain a verified connection but cannot create the match or quotation.
5. **Normalize and validate.** Validate record shape, stable source ID, HTTPS/canonical allowed host, source attribution, source/original link policy, dates, and bounded text. Keep `published_at`, `expires_at` when available, and `retrieved_at` distinct. Deduplicate within a response; reject malformed, future-dated, stale, expired, or unsupported records. Do not persist a body or excerpt unless that specific storage/caching activity and retention/deletion policy are approved.
6. **Present the evidence modestly.** Show a small number of cards inside the relevant Learn answer, with role, company, location where useful, source attribution, permitted date label, and direct source link. Quote only a short exact supported span when explicitly permitted. Label source-tag matches as tags. Explain that evidence is an example, not proof every employer requires the skill.
7. **Fail independently and honestly.** Lecture explanation remains available regardless of job evidence. Distinguish: `EvidenceFound` (qualifying, fresh, source-backed record); `NoEvidence` (approved query succeeded but no qualifying item); `RetrievalFailure` (approved lookup failed or could not be validated); `SourceNotApproved` (policy prevents the request, so no request was made). Stale/removed/rate-limited details may remain sub-states or diagnostics, but must not be collapsed into “no jobs.”

## Phase 3A contract hardening and remaining changes

The source-neutral Phase 3A change is implemented and verified: denied retrieval/display use returns `source_not_approved` without invoking a provider; valid empty results remain `no_evidence`; malformed or thrown provider results remain `failed`; the Learn UI distinguishes these states and can render validated `found` evidence. The full unit suite, typecheck, lint, build, secret scan, and diff check passed. No provider adapter, feature flag, persistence, database schema, or live-source permission changed. For any later approved integration, retain the modular-monolith/source-neutral boundary and avoid a new persistence layer. Remaining hardening ideas are:

- Extend `JobEvidenceResult` with an explicit `source_not_approved` result and map permission denials to it rather than surfacing an exception as generic retrieval failure.
- Make the source grant record the basis/review date and independently gate retrieval, metadata display, excerpt display, attribution, direct linking, and caching/retention. `conditional` and `unclear` must continue to fail closed.
- Add a source-neutral verified-evidence constructor that requires an approved grant, exact text provenance, direct match, freshness, attribution, and permitted URL. Keep metadata references structurally unable to carry an excerpt or a description-level skill assertion.
- Keep cache/storage disabled until a source's terms state retention duration, refresh, expiry/removal and deletion behavior. If later permitted, cache only the minimum card fields/exact supporting span, never full descriptions by default.
- Keep all third-party text untrusted and outside system instructions; keep provider credentials server-only. Do not add course or job evidence to unrelated AI contexts.

## Safe work that can proceed; blocked work

**Can proceed without a new source decision:** preserve and regression-test lecture grounding, explicit skill extraction, metadata/excerpt type separation, stale/failed/empty/source-not-approved states, direct-link and attribution validation, permission denial, and lesson independence using synthetic fixtures. Phase 3A has added the typed source-not-approved contract and Learn presentation. Use the existing Remote OK pilot only within the already-approved cap and only when deliberately testing that development pilot.

**Still blocked:** a live Arbeitnow/Himalayas adapter; description ingestion for either; excerpt presentation; third-party content caching/persistence/redistribution; and any production activation. These require clear applicable permission for Miva Buddy's exact educational display, attribution/link behavior, cache TTL, removal/deletion, rate limits and use of underlying employer content. An accessible API, returned description, successful test, provider attribution request, or another project's implementation does not itself settle those rights. If there is no clear license/terms grant, the product should show no excerpt-backed job evidence.

## Future company-specific interview preparation

Transfer the handoff's **evidence principles**, not Desktop code or storage/IPC architecture:

- Hacker News/Algolia is a discovery/search source, not a verified interview database. Handoff samples were small and mixed; a company keyword plus “interview” does not prove a first-person account. The post timestamp is not necessarily the interview-event date. Establish source rights for retrieval, excerpts, storage, attribution, model processing and removal before integration. See the [Algolia HN Search API](https://hn.algolia.com/api) and [Hacker News API](https://github.com/HackerNews/API).
- Match company identity deterministically and keep role, level and geography only when stated. Qualify first-person participation; separate the interview-event date, publication date and retrieval/last-check date. Unknown event dates must remain unknown—not “recent.” Preserve conflicting accounts rather than averaging them into company-wide claims.
- Treat every account as anecdotal. Show source, role/date context, sample count and freshness; each company-specific factual claim must trace to a qualifying account. One report is not a prediction or a company's standard process.
- LeetCode Discuss remains link-out/manual discovery only unless an approved API or explicit permission changes the documented restriction. The handoff cites [LeetCode Terms](https://leetcode.com/terms/); do not scrape, crawl, cache, or reproduce those posts. Do not copy Desktop datasets or source code.
- The existing V2 roadmap's first-party, opt-in submissions are a possible future alternative, but require separate product approval for consent, privacy, moderation, withdrawal and retention. Nothing in this audit authorizes collection or publication.

No interview retrieval, scraping, interface, database, or other V2 feature is implemented or approved here.

## Readiness milestones and acceptance tests

1. **Permission and source ledger:** for each source record allowed API endpoints, intended purpose, allowed metadata/text, attribution, link target, rate limit, cache TTL, expiry/removal and deletion obligations, and review date. Acceptance: missing/conditional rights deny the activity; no live request occurs when retrieval is not approved.
2. **Source-neutral outcomes and grounding:** `SourceNotApproved` and the pre-query gate are implemented in Phase 3A. Future acceptance still requires selecting a small concept set only from page-backed course evidence and proving forged/model-only skills cannot trigger lookup; no evidence, blocked source and API failure must remain observably distinct.
3. **One approved adapter pilot:** only after the permission gate, implement one provider behind `JobEvidenceProvider`. Acceptance with synthetic fixtures plus a strictly bounded authorized live evaluation: schema/URL/source validation; exact source-text match; citation to course page and job span; source attribution/link; publication/expiry/retrieval freshness; rate-limit, empty, stale, removed and failure behavior; no unauthorized fields or caching; no fake live records.
4. **Learn integration and release gate:** display a few contextual evidence cards without blocking the lesson. Acceptance: browser tests cover grounded answer with evidence, no evidence, unapproved source, retrieval failure, mobile/accessibility, source link and labels; security tests verify owner isolation and no credentials/source bodies in client logs; release remains blocked until the source and content-use approvals cover production.
5. **Interview research (separate V2):** obtain source rights or approve first-party consent model before retrieval. Acceptance: first-person/company/role validation, separate event/publication/retrieval dates, anecdotal labels, per-claim citations, duplicate handling, stale/removal behavior, and no automated LeetCode Discuss collection.

### Unresolved risks / decisions

- Himalayas API display language and its general terms do not clearly settle excerpt rights, underlying employer rights, persistent caching, or employer-original URLs.
- Arbeitnow exposes descriptions but does not clearly grant their reuse; its feed needs broad/local filtering and its timestamp/target URL semantics require validation.
- Remote OK tag matches are useful contextual metadata but do not complete the product's excerpt-backed evidence goal.
- The current process-local Remote OK request counter is not suitable as production-wide quota enforcement.
- Search coverage, Nigeria/worldwide eligibility, link persistence, closure detection, and duplicate quality have not been validated for Himalayas or Arbeitnow in Miva Buddy Web. No new source API requests were made for this audit.
- The named result labels in the handoff are conceptual; Web uses lowercase discriminants such as `source_not_approved`. Keep the public UI copy understandable and preserve the distinction between a disabled/unauthorized source and an empty search.

## Phase 3B implementation addendum — Himalayas metadata-only (2026-10-09)

The Phase 3 audit was a readiness snapshot; its “no adapter exists” and “do not add another live integration yet” statements describe the pre-Phase-3B state. At the user's direction, the official [Himalayas API reference](https://himalayas.app/docs/remote-jobs-api) and [Terms and Conditions](https://himalayas.app/terms) were reviewed for a narrow implementation. The API reference describes an application-oriented keyword-search API and expressly requires a visible Himalayas link and source credit for app displays. We therefore implemented an opt-in, server-side **metadata/link-only related-listing** adapter. It is not a description-evidence integration and does not satisfy M8's excerpt-backed gate.

The API-specific display language supports retrieval/search and attributed metadata presentation; the general Terms contain broad public-display/copy/distribution and automated-extraction restrictions. We interpret the API-specific grant narrowly for the fields exposed in the UI, while treating description access for validation, excerpt display, persistent/temporary application caching, and redistribution of employer-authored text as unresolved and omitting those activities. The response is transiently received by the server as required for API use, but descriptions are not read by normalization, returned to the client, logged, persisted, or cached. The results contain no verified skill claim; they are related listings only.

The adapter sends only one canonical course-grounded skill term, uses the documented search endpoint and first/recent page, caps its response body and displayed records, enforces API refresh/publication/expiry freshness checks, applies a conservative four-request-per-process/day and 60-second spacing limit, and requires `HIMALAYAS_METADATA_ENABLED=true`. The process-local cap is not production-wide enforcement. No live API request was made for this implementation; tests use synthetic responses. Remote OK remains a separate development-only pilot.

**What changed:** metadata-only Himalayas search and rendering are now implemented; the following remain intentionally unavailable: description-based skill verification, excerpts, tags as evidence, caching/persistence, unbounded pagination, and any claim that a listing is still open after retrieval. M8 remains blocked pending permission-backed excerpt evidence; this metadata path is not presented as an equivalent substitute. The V2 interview evidence plan remains unchanged.
