# Milestone 8 — Contextual industry evidence

## Current implementation state

M8 remains **Blocked** on its excerpt-backed live-evidence acceptance criteria. Its development-only synthetic preview is retained, and a separate Remote OK metadata-only pilot is approved in development. That pilot does not claim a skill appears in job-description text and does not satisfy the excerpt-evidence requirements below.

The grounded Learn response flow may return a development-only demonstration when retrieved course passages directly mention a skill in the canonical registry. The server derives that skill from retrieved course chunks—not from the student's question or model response. The strict `IndustryDemo` schema is deliberately distinct from `JobEvidenceItem`, contains no source URL, and displays an unmissable “DEMONSTRATION ONLY — NOT A REAL JOB POSTING” label. It is not saved to the database. The server function returns no demo in production.

Real-source building blocks include pure Remotive/Greenhouse/Ashby/Lever normalizers and a server-only Remote OK adapter. The Remote OK adapter is wired only into development grounded Learn when `REMOTEOK_METADATA_PILOT=true`; it returns at most three metadata-only, directly linked cards, uses a conservative process-local request cap, does not read descriptions into normalized output, and does not cache or persist records. Exact overlaps with Remote OK's own tags may be displayed as tag matches, accompanied by an explicit notice that the description was not checked. Empty, failed, and rate-limited states remain distinct and do not affect the saved lesson. Remotive remains unselected and unwired; ATS integrations remain pure normalizers. Full source decision and boundaries are in [`milestone-7-job-evidence-source-evaluation.md`](milestone-7-job-evidence-source-evaluation.md).

The Phase 3B Himalayas adapter is an additional opt-in metadata-only discovery path (`HIMALAYAS_METADATA_ENABLED=true`), separate from Remote OK. Based on the API-specific documentation, it performs one bounded keyword search using only a canonical skill grounded in retrieved course material and can render up to three titled listings with company, publication/retrieval dates, visible Himalayas attribution, and a direct Himalayas listing link. It does not inspect or display job descriptions/excerpts, tags, or claim that an employer requires the course skill; students see “related listings” only. It performs no persistence or cache. The broad general Terms leave description reuse/processing, retention, and third-party employer-text rights unclear, so those activities remain out of scope. Details and the limited interpretation are recorded in the M7 source decision.

### Phase 3A — source approval and failure-state contract

The shared result contract now includes `source_not_approved`, distinct from `no_evidence` and `failed`. `src/server/job-evidence/search.ts` checks retrieval and requested display permissions before invoking a provider, returns `source_not_approved` without making a request when a required permission is missing/unclear/conditional/prohibited, preserves valid no-evidence results, and maps provider exceptions or malformed results to a safe failure. The Remote OK route uses this boundary for its existing metadata-only grant; its development flag, request cap, freshness, no-store behavior, and output fields are unchanged. The Learn UI renders validated `found` items with the excerpt, source attribution and listing link; it separately labels no evidence, retrieval failure, source-not-approved and rate-limited states. Course explanations remain persisted and usable independently.

### Phase 3C — grounded Learn to related-job discovery

- **Implemented:** the server calls `searchCourseHimalayasReferences` only after retrieved course chunks support a canonical skill. The helper sends only that canonical skill to the existing metadata adapter; unsupported questions, absent course evidence, disabled feature flag, or no canonical skill cannot trigger a search. The saved lecture explanation remains independent of the optional provider result. Remote OK's route and pilot configuration are unchanged.
- **Student states:** validated listings appear in a visually separate “related listings” section with title, company, source credit, publication/retrieval dates, and direct listing link; the UI explicitly says the job description was not checked. `no_evidence` means an eligible search completed without qualifying current listings. `failed` now says listings may be temporarily unavailable or could not be verified as current, and that the lesson is unaffected. `source_not_approved` retains its distinct permission-gate explanation. Synthetic preview records remain clearly labeled and development-only.
- **Freshness and limits:** no adapter freshness, per-listing validation, permission, request-limit, attribution, or persistence behavior was relaxed. In particular, the provider feed must still be refreshed within 48 hours and individual posts must pass publication/expiry/link checks.
- **Verification:** focused course-to-Himalayas, UI-state, and provider tests passed (36 tests); full `npm test` passed (172 tests, 2 optional skips); `npm run typecheck`, `npm run lint`, `npm run build`, `npm run check:secrets`, and `git diff --check` passed. Chromium desktop/mobile Playwright: 16 passed, 16 hosted/configuration tests intentionally skipped. A separate hosted synthetic grounded-Learn journey passed in an isolated development copy both with Himalayas disabled and with the metadata flag enabled. The enabled run used one bounded API request from the SQL keyword in the seeded, course-grounded passage and asserted that Learn rendered either a validated related-listing section or a clear provider status. The API response branch/count was not recorded by the test; the last explicitly observed live adapter result had 17 rows and zero accepted due to stale feed freshness. The sanitized `npm run check:hosted-config` reports `DATABASE_URL` connected when run with network access; the restricted sandbox's DNS failure was environmental.
- **Browser test diagnosis:** the first hosted E2E reused an already-running development server on port 3000 (`reuseExistingServer`), so its configured fake-provider server environment did not apply and the page had noninteractive/stale client assets. A subsequent production-mode comparison also used fake embeddings, which the application intentionally rejects in production. Neither indicated an application regression. Running the same synthetic journey against a clean, isolated development server and separate build output passed. No production flags or credentials were changed.
- **Remaining gate:** description-level requirements are not verified; this remains related-job discovery only and does not meet M8's excerpt-backed acceptance gate. The provider's feed freshness may independently yield the honest stale/unavailable state without affecting Learn.

## Not implemented / not verified

- Remote OK retrieval and metadata display are approved only for the development pilot; excerpt display and caching remain denied/unresolved, and production is disabled.
- No real listing is stored or cached. A prior controlled live API evaluation was rejected by the 48-hour feed freshness gate (17 rows received, zero accepted). The Phase 3C hosted synthetic Learn journey passed; its one live-enabled run permits either validated cards or the honest provider status and does not assert that listings were fresh/available.
- No live provider coverage, closure/removal, availability, or manual provenance test was run.
- Remote OK metadata-and-link-only output is shown only in the opt-in development pilot, under the user's limited approval. It is explicitly not represented as description-level skill evidence.
- The Remotive request limit guard is process-local and is insufficient for a multi-instance public service; do not use it as production quota enforcement.
- Automated disappeared-listing detection remains unverified; no per-listing status probe was made to avoid extra source requests. The hosted synthetic Learn-to-metadata journey passed in Phase 3C, and the adapter's no-result, source-failure, rate-limit, freshness, and permission states are covered by synthetic unit tests.

## Gate and next work

Do not revisit source terms or conduct outreach in this phase. M8 remains blocked on the distinct excerpt-backed acceptance gate; the metadata pilot is not a substitute.
