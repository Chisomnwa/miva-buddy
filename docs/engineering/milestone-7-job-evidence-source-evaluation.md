# Milestone 7 — Job-evidence source evaluation

## Status and decision

**Verification in progress for an explicitly scoped Remote OK development pilot.** The user approved retrieval and display of Remote OK listing metadata with attribution and direct listing links. This does not approve excerpt display or caching. The source-neutral contract, synthetic normalizers, freshness checks, attribution handling, matching, and fail-closed permissions remain in force. Remotive remains unselected and unwired; this decision does not change its status.

This is a source/permission decision, not a product change. The original M7 decision was **go only for the narrowly scoped Remote OK development metadata pilot** described below; that pilot does not complete M7's broader verification gate or change M8's excerpt-backed acceptance criteria. The later Himalayas metadata-only scope is documented separately below; excerpt use and caching remain no-go.

## Source-independent boundary

- `src/contracts/job-evidence.ts` defines normalized excerpt evidence, a separate `references_only` metadata/link outcome, and distinct no-evidence, failure, rate-limit, stale, and removed outcomes. A metadata-only reference cannot carry an excerpt or matched-skill claim.
- `src/server/job-evidence/provider.ts` defines a source-neutral `search` interface. Product code receives no source-specific record assumptions.
- `src/server/job-evidence/normalizers.ts` contains pure shape normalizers for synthetic Remotive, Greenhouse, Ashby, and Lever records. It performs no HTTP requests and writes no data.
- `src/server/job-evidence/matching.ts`, `freshness.ts`, and `permissions.ts` implement whole-term/approved-alias checks, bounded direct-sentence selection, caller-supplied freshness limits, attribution fields, and fail-closed activity permissions. The Remote OK adapter encodes only the limited grant described below; no broader source grant is configured.
- `tests/fixtures/job-evidence.ts` contains explicitly synthetic `example.invalid` data and status cases. It lives under tests and is not wired to runtime provider selection.
- `tests/unit/job-evidence-contract.test.ts` exercises fixture outcomes and synthetic source shapes, direct matches/false positives, attribution and HTTPS requirements, metadata-only separation, stale/future timestamps, and permission denials.

The contracts themselves do not grant source rights. Each adapter must enforce the activity-specific permission recorded for that source, including permitted display fields, attribution, retention/cache limits, link behavior, freshness, and deletion/closure rules. Description-level evidence claims still require a directly verified excerpt; model memory or source tags are not evidence of description text.

### Remote OK metadata pilot decision (2026-10-08)

The user's approved scope is limited to Remote OK's public JSON API retrieval and metadata display under the published feed-sharing conditions. The development-only Learn pilot requests one canonical course skill through the documented `tags=dev,<skill>` filter, selects at most three software-engineering listings, and returns only title, company, location, source tags, available listing date, Remote OK attribution, the direct Remote OK listing URL, and retrieval timestamp. The server never reads `description` into a normalized result, never stores listing data, and uses `cache: "no-store"` plus `Cache-Control: no-store`. The UI explicitly says the job descriptions were not checked; it can report a source-tag overlap only and cannot claim that the lecture skill appears in the job description. A source-provided tag is displayed as a tag, not an excerpt-backed requirement. A four-request per process per UTC day cap and 60-second minimum spacing are conservative application limits, not Remote OK's published quota and not shared production enforcement.

The pilot is opt-in via `REMOTEOK_METADATA_PILOT=true`, and the server additionally requires development mode. The adapter's upstream HTTP request is made only after grounded Learn has persisted its answer and only when a canonical skill is explicitly present in the retrieved course evidence. Source failures do not undo or alter that lesson. No source response is stored. Results must have a published date no older than 30 days at retrieval; missing, invalid, future, or older dates fail closed. This is Miva's conservative pilot freshness policy, not a Remote OK promise that a listing remains open. The remote API's availability of a listing does not guarantee the listing remains live when a student follows its link.

The feature requires `REMOTEOK_METADATA_PILOT=true` and `NODE_ENV=development`. It is disabled in production. Upstream calls are capped at four per process per UTC day and at least 60 seconds apart; this is a conservative local pilot limit, not a Remote OK-published quota or a multi-instance production safeguard. There is no persistent or in-memory response cache. Per-listing availability is not rechecked with extra requests; a card records retrieval date and links directly to the Remote OK listing, which may close after retrieval.

### Himalayas metadata-only integration (2026-10-09)

The official [Remote Jobs API reference](https://himalayas.app/docs/remote-jobs-api) describes an unauthenticated keyword-search API for developers and applications. It explicitly contemplates displaying job data in an app when the display includes a visible Himalayas link and source credit. The API documents title, company name, publication/expiry dates, and an application link hosted on Himalayas. This is the basis for the limited metadata-only integration; it is not a blanket licence for all API fields or the underlying employer content.

The [general Terms and Conditions](https://himalayas.app/terms) contain broad restrictions on public display, copying/distribution and automated extraction, while also qualifying restrictions by other permissions in the Terms. The API-specific documentation appears to authorize API retrieval/search and attributed metadata display for apps, but it does not clearly settle verbatim description/excerpt reuse, whether description text may be processed for skill proof, retention/cache/persistence, or reuse rights in employer-authored text. Accordingly, the adapter does not inspect/project excerpts or descriptions, does not match job text to skills, and does not store or cache any response. A request necessarily receives a response payload transiently; description fields are not accessed by the normalizer or returned to the browser. This is a narrow reading of the API-specific documentation, not legal advice or a conclusion about third-party rights.

The server-only adapter calls only the documented `/jobs/api/search` endpoint, sends one canonical skill explicitly found in retrieved course passages (never the lecture, student question, transcript, or profile), requests the recent first page, disables HTTP caching/redirects, caps response bytes, applies a six-second timeout, and displays at most three current listings. It validates title, company, stable ID, HTTPS Himalayas listing host, publication date, expiry, and API refresh timestamp. Postings older than 30 days, future-dated, expired, or malformed are omitted; an API refresh marker older than 48 hours fails closed. Four requests per process/UTC day and 60-second spacing are conservative app safeguards; they are not provider-published quotas or multi-instance enforcement. The `HIMALAYAS_METADATA_ENABLED=true` feature flag is required; no credential is needed.

The Learn card is explicitly **related listing discovery, not verified skill evidence**. It displays title, company, publication/retrieval dates, source credit and the direct Himalayas application/listing URL. It does not display location, tags, excerpt, salary, description, or an employer-requirement claim. Remote OK remains its own separate, development-only pilot. No live Himalayas API request was made during implementation; automated tests use synthetic fixtures.

**Controlled live result (2026-10-08):** one successful low-volume request through the adapter returned three software-role candidates with a Python source tag. Their published dates were 47, 53, and 76 days before retrieval, so the 30-day freshness filter correctly removed all three; the final adapter returned `no_evidence` and would render no stale cards. The test emitted only the allowlisted public metadata before the freshness cutoff was added; it did not save it. A subsequent request through the updated adapter returned `no_evidence`. The unauthenticated sandbox attempt failed safely; only the approved network-enabled test made live requests. No description text was logged, displayed, or persisted.

The hosted grounded-Learn E2E could not be run in this verification: the safe hosted-config check found the required variables syntactically present but PostgreSQL connectivity was not established. Unit/UI contract coverage, local E2E, typecheck, lint, build, and secret-safety results are recorded after this section is updated. **Still not approved/implemented:** description excerpt display, storing or caching any listing data, broad job search, applying, or production activation. M7 remains in Verification until the full hosted Learn path can be exercised; excerpt-backed direct evidence remains a separate M8 acceptance requirement.

### Remotive adapter implementation boundary (2026-10-08)

`src/server/job-evidence/remotive-provider.ts` is a server-only, source-neutral adapter implementation that can be exercised using mocked responses. It requires explicit `permitted` grants for retrieval and metadata display before making a request, and a separate explicit grant for excerpt display. With excerpt display not permitted it can produce only the distinct `references_only` shape; that path does not include descriptions or a matched-skill assertion. It disables HTTP caching, stores nothing, caps each response to ten rows, requests a single supplied search term, follows no redirects, has an eight-second timeout, validates Remotive listing URLs, and returns safe typed failures. Its in-memory quota guard is only process-local (four requests per UTC date and at least 30 seconds apart), so it is **not sufficient for a horizontally scaled or restartable public deployment**. It is not wired to user traffic; do not enable it without a shared quota strategy and activity-specific approval. Automated tests use synthetic mocked payloads only.

As checked on 2026-10-08, the public API page allows developers to share jobs further if each item links to its Remotive listing and credits Remotive; it also bars submitting those jobs to third-party job websites, says the data is delayed by 24 hours, and warns against gating a displayed job behind signup/email collection. The separate Terms of Use, updated 2026-03-18 (page footer updated 2026-10-07), prohibit automated extraction without written permission and copying, reproducing, redistributing, publishing, or making listing/company content available to third parties. These provisions leave unclear whether API sharing permits Miva's contextual educational card, whether metadata-only is covered, whether a short excerpt is covered, and whether API wording overrides the general restrictions. Accordingly, do not publish/cache real data based on the API page alone. The API reference recommends no more than four calls per day and warns of blocking above two per minute. A prior evaluation day made five calls; **no further Remotive request was made on 2026-10-08**. See [API terms](https://remotive.com/remote-jobs/api), [API usage documentation](https://github.com/remotive-com/remote-jobs-api), and [general Terms of Use](https://remotive.com/terms-of-use).

### Metadata-and-link-only fallback

A result with title/company/location and a source link but no excerpt can be represented as a `references_only` result. This can offer a student a relevant place to read more, but it is **not evidence that the course skill appears in the posting** unless a source-provided structured field itself directly names that skill. The reviewed ATS metadata generally provides role/company/location and a posting URL, not a reliable normalized skills field. Therefore, ordinary metadata-only cards cannot satisfy the current product's direct-support rule or replace excerpt evidence. They might be a separately labeled “related role to explore” affordance, but that is a product decision, not an equivalent implementation of contextual industry evidence.

Metadata-only use is not automatically permitted: titles, company/location fields, and compilations of listings can remain within a provider's “job listings/company data” restrictions or outside its documented API purpose. Remotive's sharing/link/source requirements still apply; ATS Miva display remains unclear. The code now models `references_only` separately, forbids excerpt/matched-skill fields in that result, and keeps it out of `found` evidence. It does not render or persist these references in the app.

Work that can proceed without external rights includes synthetic record normalization for the four source shapes, direct term/approved-alias matching, excerpt selection, attribution metadata, freshness evaluation, fail-closed permission guards, and M8 UI validation using a synthetic demo contract. Greenhouse/Ashby/Lever APIs describe employer-careers-site use, with Ashby explicitly warning that authenticated `jobPosting.list` may return unlisted postings unless `listedOnly=true`; Lever's API documentation says it is intended for custom public job sites and allows CORS only from the employer's company domains/subdomains. ### Lilo Companion repository: source-code review (2026-10-08)

The public [`HackedRico/lilo-companion` repository](https://github.com/HackedRico/lilo-companion) was inspected at source level, including `scripts/ingest-ikb.ts`, `data/boards.json`, `main/ikb/`, and `main/pipeline/`. No job-board endpoint was requested for this review. No Lilo code or dataset was copied into Miva Buddy.

- **Sources:** the ingestion script requests Greenhouse's public Job Board endpoint (`boards-api.greenhouse.io/.../jobs?content=true`), Ashby's public job-board posting endpoint (`api.ashbyhq.com/posting-api/job-board/...`), and Lever's public postings endpoint (`api.lever.co/v0/postings/...?...mode=json`). The board registry contains 30 configured employer boards: 23 Greenhouse, 6 Ashby, and 1 Lever. These are employer ATS endpoints, not an API aggregator or paid job-data service. The inspected code uses no credentials and describes the endpoints as those used by the employers' own job pages.
- **Retrieval and filtering:** running the repository's `npm run ingest` invokes one sequential pull per configured board. It converts source HTML/plain text to text, classifies titles into software-engineering role families, excludes non-engineering and boilerplate material, segments descriptions into bounded sentences, tags sentences against a local tools/practices vocabulary, and retains only postings with at least one tagged sentence. It caps retained material at 80 postings per board and 12 evidence sentences per posting. A failed board is skipped and reported; this can make a partial snapshot unless an operator notices the failure.
- **Storage and refresh:** the script overwrites `data/ikb.json` with normalized posting metadata and the retained sentence excerpts. That static snapshot is loaded into in-memory maps and search indexes at runtime. The repository has a manual `ingest` package script; the inspected workflow list showed a build workflow, not a scheduled ingestion refresh. The ingestion output contains no explicit retrieval timestamp, expiry policy, closed-post reconciliation, or tombstone handling. Thus freshness and removal are operator responsibilities in the reviewed implementation, not a demonstrated automatic guarantee.
- **Lecture-to-evidence flow:** the app extracts a bounded set of lecture concepts, maps them to a controlled taxonomy and nearby terms from the local evidence index, and may ask the model for candidate vocabulary. Deterministic resolution drops terms absent from the indexed tagged vocabulary. If no fixed term survives, a retrieval step selects matching sentences; a model-named skill is retained only when its meaningful words appear in the cited sentence text. Cards use verbatim indexed posting sentences, associated with company/title/direct posting URL, with at most one sentence per company in the evidence selection. This is an implementation pattern for grounding—not proof that storing or displaying the excerpts is licensed.
- **License distinction:** the repository declares Apache-2.0 for its software. That license does not grant rights to third-party employer job descriptions, ATS-returned content, or Lilo's checked-in evidence corpus. Neither a public endpoint nor Lilo's own publication of a static snapshot establishes permission for Miva Buddy. Do not copy the source code, board registry, or evidence dataset; independently implement a source-neutral adapter and obtain rights for any Miva source material.

### Comparative M7 assessment and recommendation

The Lilo pattern is materially different from Remotive and Adzuna: it fetches directly from a deliberately selected set of employers' public ATS boards, avoiding a paid aggregator as a technical dependency and preserving direct employer URLs. It also shifts the hard parts to Miva Buddy: every board must be selected and maintained, source-specific rights need to be resolved, geographic/student-level coverage must be measured, and freshness/removal must be designed across providers. Remotive is simpler as a single feed but has unresolved constraints for contextual excerpt cards and requires a Remotive link/source attribution; Adzuna expressly supports publishing its listings with prescribed attribution, but its terms impose API limits, a narrow 14-day evaluation for other organizational uses, and possible licensing for ongoing use.
